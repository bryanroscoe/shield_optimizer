# Screenshot retention — 2026-10-17

Originally based on `dccfe99a805ffcb0c11f32a4fa9f227306ba1cf3`; now integrates `mobile-parity-pass` `5e80c0efd6620060bb03d5c354815990303628ab`, including reviewed header PR191. RAM PR192 remains separate. Storage behavior and fixtures are unchanged by integration. Independent source review found no code blocker; local inspection of tempfile 3.27.0 confirms Windows omits replacement flags and the Unix/Android fallback uses hard-link then best-effort unlink. These source checks are not actual platform acceptance. Header evidence is retained from PR191; no new UI pixels are introduced by this storage fix.

The previous shared `take_screenshot` generated a filename at second resolution and used `tokio::fs::write`, so a second capture for the same serial/time replaced the earlier PNG. It now stages complete bytes in the same directory, then uses `NamedTempFile::persist_noclobber` to claim the original filename without replacing an existing destination or bounded numeric suffixes (2) through (1000). A racing capture retries the next candidate. There is no preflight existence-check race. The existing `tempfile` dependency moves from dev-only to production; mobile already uses the same facility for downloaded files.

The directory, first filename format, PNG validation, and `{ path, base64 }` response remain unchanged. Returned path names the actual published file; base64 still encodes the captured bytes. Existing captures are neither deleted nor migrated. Partial write, staging/publication errors and name exhaustion return errors before any success response; temporary-file ownership attempts cleanup of failed staging on a best-effort basis. On some platforms tempfile uses a non-overwriting hard-link fallback: if unlink fails, an additional temporary link can remain even after the complete destination is saved. This does not guarantee universal atomic rename, power-loss durability or cleanup under every filesystem failure.
